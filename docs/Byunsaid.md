# 📢 통신SW설계 프로젝트 발표 조건 정리 및 디펜스 가이드 (`Byunsaid`)

팀원들과 함께 공유하기 위해 **교수님 제시 7대 발표/설계 조건에 맞춘 상세 정리(특히 3번 스레드/동기화 구성, 4번 시스템/보안 구축)** 및 **압박 질문 대비 디펜스 논리**를 정리한 문서입니다.

---

## 1. 주제 (Topic)
* **멀티 클라이언트 키오스크 및 주방/고객 실시간 연동 시스템**
  * 독립된 2대의 매장 키오스크(보다수 커피, 김밥천국)와 주방 화면, 고객용 가상 모바일 폰이 중앙 FastAPI 서버 및 **SQLite3 DB(`kiosk.db`)**를 통해 실시간으로 연동되는 통합 주문·조리·호출 시스템

---

## 2. 배경 설명 (주제 선택 이유)
1. **현실 매장의 단절된 주문-조리-호출 프로세스 개선**
   * 최근 카페와 분식점 등 소규모 외식 매장에서도 무인 키오스크 도입이 보편화되었으나, **① 매장별 상이한 커스텀 옵션(음료 온도 vs 알레르기/기호 식품 제외)** 처리, **② 주방 조리 현황판(KDS, Kitchen Display System)**, **③ 고객 진동벨/모바일 호출 시스템**이 서로 연동되지 않아 직원이 직접 번호를 부르거나 종이 영수증을 확인하는 비효율이 발생함.
2. **멀티 클라이언트 통신 및 스레드 설계의 최적 실습 도메인**
   * 단순 1:1 통신이 아니라 **주문 생성자(키오스크 1·2)**, **상태 처리자(주방 화면)**, **알림 수신자(고객용 가상 모바일 폰)**라는 서로 다른 역할을 가진 **4개의 독립 클라이언트가 단일 중앙 서버와 실시간으로 데이터를 주고받는 구조**를 구현함으로써, 멀티클라이언트 통신·스레드 분리·보안 인증을 종합적으로 설계하고 검증하기에 가장 적합한 주제임.

## 3. 구성 (서버/클라이언트 역할, 스레드 및 스레드 동기화 상세)

### (1) 서버의 역할 (`server.py`)
* **역할**: 매장 내 모든 비즈니스 로직과 데이터 흐름을 중재하는 **중앙 집중형 제어 허브 (REST API 백엔드)**
* **핵심 기능**:
  * 키오스크 1·2로부터 주문 데이터 수신 및 유효성 검증
  * SQLite3 DB(`kiosk.db`)에 주문(`orders`) 및 세부 옵션(`order_items`) 트랜잭션 기록
  * 주방 디스플레이의 주문 조회 및 조리 상태 변경(`PENDING` $\rightarrow$ `COOKING` $\rightarrow$ `COMPLETED`) 처리
  * 고객용 가상 모바일 폰의 주문 상태 변화 알림 제공
* **멀티클라이언트 지원 여부**: **완벽 지원**
  * `FastAPI` + 비동기 ASGI 서버인 `Uvicorn`을 채택하여 기본적으로 멀티 워커 및 스레드 풀(Thread Pool)을 통해 여러 대의 클라이언트가 동시에 요청을 보내도 블로킹(지연) 없이 병렬 처리함.

---

### (2) 클라이언트의 역할 (독립된 4개 기기)
1. **보다수 커피 키오스크 (`kiosk_client1.py`)**:
   * 음료 중심 주문 기기 (`HOT`/`ICE` 선택, 포장/매장, 수저 옵션)
   * 장바구니 계산 및 서버로 주문 데이터 전송
2. **김밥천국 키오스크 (`kiosk_client2.py`)**:
   * 분식/식사 중심 주문 기기 (김밥류 전용 `당근 제외`/`오이 제외`, 포장/매장, 수저 옵션)
   * 장바구니 계산 및 서버로 주문 데이터 전송
3. **주방 화면 (`kitchen_client.py`)**:
   * 미접수/조리중인 주문 목록을 1~2초 간격으로 서버에서 자동 조회(Polling)하여 주문서 카드 형태로 표시
   * 조리 진행에 따라 **[주문 접수]**, **[조리 완료]** 버튼을 눌러 서버의 상태를 변경
4. **고객용 가상 모바일 폰 (`app_client.py`)**:
   * 스마트폰 형태의 UI 창을 띄워 고객의 주문 번호를 기반으로 상태를 1~2초 간격 자동 조회(Polling)
   * 주방에서 상태를 변경하면 실시간으로 **"조리 시작 안내"**, **"조리 완료 픽업 알림"**을 모바일 알림톡/문자 배너 형태로 화면에 표시

---

### (3) 쓰레드(Thread) 구성 여부
* **구성 여부**: **클라이언트 측에 백그라운드 멀티스레드(`threading.Thread`) 적극 구성**
* **스레드 도입 이유**:
  * **키오스크 (1회성 작업 스레드)**: 결제 및 서버 전송(`requests.post`) 시 네트워크 응답 대기 시간 동안 Tkinter GUI 메인 화면이 멈추거나 튕기는 'UI 렉(Freezing)'을 방지하기 위해 별도 스레드로 통신 분리.
  * **주방 화면 & 고객용 가상 모바일 폰 (무한 반복 데몬 스레드)**: 사용자 입력(마우스 클릭 등)을 처리하는 GUI 메인 루프와 별개로, 1~2초 주기로 서버에 지속적으로 최신 상태를 요청하는 폴링(Polling) 루프를 백그라운드 스레드로 구동.

---

### (4) 쓰레드 동기화 사용 여부 및 처리 방법 (★ 핵심 평가 항목)

* **결론**: 파이썬 애플리케이션 코드 내부의 **명시적 스레드 락(`threading.Lock`, `Mutex`, `Semaphore`)은 '미사용'**
* **왜 수업 때 예제처럼 파이썬 Lock을 쓰지 않았는가? (미사용 이유)**:
  * 수업 시간 예제에서 동기화를 안 했던 이유와 마찬가지로, **프로세스 내부 메모리(In-Memory)에 공유 전역 변수(공통 메모리)를 두지 않는 구조로 설계**했기 때문임.
  * 여러 키오스크가 동시에 주문하고 주방이 상태를 바꿀 때 충돌이 나는 "공통 데이터"는 파이썬 전역 변수(List/Dict)가 아니라 **외부의 'SQLite3 데이터베이스(`kiosk.db`)'에만 존재**함.
  * 만약 서버 메모리에 공통 리스트를 두고 동기화를 했다면, 서버 프로세스가 재시작될 때 주문 내역이 모두 증발하는 치명적인 결함이 발생함.
* **그렇다면 동시성 충돌은 어떻게 처리(동기화)했는가? (처리 방법)**:
  1. **서버-클라이언트 간 데이터 동기화 $\rightarrow$ SQLite3 DB 트랜잭션(ACID) 및 WAL 모드에 위임**:
     * 다중 클라이언트가 동시에 같은 주문이나 테이블에 접근할 때 생기는 경쟁 상태(Race Condition)는 **SQLite3 엔진의 트랜잭션(ACID)과 `WAL(Write-Ahead Logging)` 동시성 잠금**이 완벽히 직렬화하여 처리함. 즉, 소프트웨어 메모리 락 대신 **DB 계층의 트랜잭션**으로 동기화를 해결함.
  2. **클라이언트 내부 GUI 스레드 안전성 $\rightarrow$ 메시지 큐 위임(`root.after`) 처리**:
     * 백그라운드 통신 스레드가 Tkinter 위젯 메모리를 직접 건드리면 충돌(Crash)이 발생하므로, 통신 결과 데이터는 `root.after()` 메서드를 호출하여 **Tkinter 메인 스레드의 이벤트 큐(Message Queue)로 안전하게 위임 전달**하여 처리함.

## 4. 시스템 구축 (UI, DB, 인증, 암호화, 기능 및 AI 활용)

### (1) UI 형태
* **서버**:
  * 백그라운드에서 동작하는 고성능 API 서비스 형태
  * 콘솔 로그창(실시간 패킷/접속 로그) 및 브라우저 기반 Swagger UI(`https://127.0.0.1:8443/docs`)를 통해 API 상태 확인 가능
* **클라이언트 4종 (Python `Tkinter` / `CustomTkinter` 기반)**:
  * **키오스크 1·2**: 대형 터치스크린 형태 (카테고리 탭, 메뉴 그리드 버튼, 하단 옵션 라디오/체크박스, 우측 스크롤 장바구니, 대형 결제 버튼)
  * **주방 화면**: 가로형 와이드 모니터 형태 (현재 접수 대기 중인 주문 카드들이 실시간으로 추가되는 KDS 대시보드 구조)
  * **고객용 가상 모바일 폰**: 360x640 비율의 **스마트폰 외형 프레임 UI** (상단 상태바, 주문 내역 및 중앙 팝업/알림톡 배너)

---

### (2) 데이터베이스 유무 (DB 연결)
* **유무**: **SQLite3 데이터베이스(`kiosk.db`) 구축 및 연결 필수 적용** (Python 내장 `sqlite3` 드라이버, `WAL` 모드 적용)
* **테이블 4종 구조**:
  1. `stores`: 매장 고유 ID (`KIOSK_01`, `KIOSK_02`), 매장명, 접속 IP
  2. `menus`: 메뉴 ID, 소속 매장, 카테고리, 메뉴명, 단가 (총 23종 초기 자동 적재)
  3. `orders`: 주문 고유번호, 매장 ID, 포장 여부, 수저 여부, 총 금액, 주문 상태(`PENDING` $\rightarrow$ `COOKING` $\rightarrow$ `COMPLETED`), 접수알림여부, 완료알림여부, 주문시간
  4. `order_items`: 주문 세부 품목 ID, 주문 ID, 메뉴 ID, 수량, `HOT`/`ICE` 옵션, 당근제외 여부, 오이제외 여부

---

### (3) 인증 유무 (아이디, 패스워드 vs API Key)
* **인증 방식**: **기기 인증용 API Key 헤더 검증 (`access_token`)**
* **ID/PW 대신 API Key를 선택한 구체적 이유**:
  * 키오스크, 주방 화면, 전용 모바일 폰은 일반 웹사이트처럼 사람이 매번 아이디/비밀번호를 치고 로그인하는 기기가 아니라, 매장에 설치되어 24시간 가동되는 **전용 단말기(M2M, Machine-to-Machine 통신)**임.
  * 따라서 클라이언트와 서버 간 사전에 안전하게 발급·공유된 비밀 키(`access_token`)를 HTTP 요청 헤더에 포함시키고, FastAPI의 `Security(APIKeyHeader)` 미들웨어가 매 요청마다 이를 가로채 검증함.
  * 인가되지 않은 외부 컴퓨터나 해커가 임의로 주문 API를 호출하면 서버가 즉시 `403 Forbidden` 에러를 반환하고 요청을 차단함.

---

### (4) 암호화 유무 (HTTPS SSL/TLS)
* **암호화 여부**: **HTTPS (SSL/TLS) 전송 구간 암호화 적용**
* **구체적 구현**:
  * 자체 서명(Self-signed) 개인키(`key.pem`)와 인증서(`cert.pem`)를 생성
  * FastAPI/Uvicorn 서버 구동 시 SSL 파라미터(`ssl_keyfile`, `ssl_certfile`)를 지정하여 보안 포트(`8443`)로 실행
  * 클라이언트 통신 시 `https://` 프로토콜을 사용
* **도입 효과**:
  * 일반 HTTP에서는 패킷 감청 툴(Wireshark 등)로 네트워크를 엿보면 주문 내역과 헤더의 `access_token`(API 키)이 평문으로 노출됨.
  * HTTPS를 적용함으로써 **헤더(API Key)와 본문(주문 JSON) 전체가 암호화되어 패킷 스니핑 및 위변조로부터 완벽히 보호**됨.

---

### (5) 다양한 기능 구축 시스템 요약
1. **옵션 분기 처리 시스템**: 동일한 공통 옵션(포장, 수저) 위에서 매장 특성에 따라 서로 다른 세부 옵션(커피는 온도, 김밥은 식재료 제외)을 수용하는 유연한 데이터 구조
2. **비동기 상태 전이 시스템**: 주문 생성(`PENDING`) $\rightarrow$ 주방 접수(`COOKING`) $\rightarrow$ 조리 완료(`COMPLETED`)로 이어지는 3단계 생명주기 관리
3. **무상태(Stateless) 실시간 알림 시스템**: 무거운 소켓 연결 유지 대신 가벼운 1~2초 주기 HTTPS 폴링을 활용한 스마트폰 픽업 알림

### Q1. "통신SW설계 수업인데 왜 파이썬에서 `threading.Lock` 같은 스레드 동기화를 안 썼죠?"
> **모범 답변:**  
> "저희가 동기화를 무시한 것이 아니라, **공유 자원의 위치를 애플리케이션 메모리(In-Memory)에서 데이터베이스(SQLite3) 계층으로 분리하여 설계**했기 때문입니다.  
> 만약 서버 코드 내의 전역 리스트(`global list`)에 주문을 저장했다면 파이썬의 `threading.Lock`이 필수였겠지만, 서버가 재시작되면 데이터가 증발하는 치명적인 단점이 있습니다.  
> 따라서 저희는 모든 공유 상태를 중앙 **SQLite3 RDBMS(`kiosk.db`)**에 두고, 여러 클라이언트가 동시에 접근할 때 발생하는 경쟁 상태(Race Condition)를 **SQLite3 엔진의 트랜잭션(ACID)과 `WAL(Write-Ahead Logging)` 동시성 잠금**을 통해 처리하도록 설계했습니다.  
> 또한 클라이언트(`Tkinter`) 내부에서도 백그라운드 스레드는 오직 네트워크 I/O만 수행하고, 화면 갱신은 `root.after()`를 통해 **메인 스레드의 이벤트 큐로 위임(Message Passing)하는 무잠금(Lock-free) 구조**로 스레드 안전성을 보장했습니다."

### Q2. "실시간 알림이면 왜 TCP 소켓이나 WebSocket을 안 쓰고 1~2초 간격의 HTTP 폴링(Polling)을 썼나요?"
> **모범 답변:**  
> "소켓 연결(Stateful) 방식은 키오스크나 주방 기기의 네트워크가 일시적으로 끊겼을 때 재연결(Reconnection) 및 세션 유지 관리가 복잡하다는 단점이 있습니다.  
> 반면 매장 주문 및 조리 완료 알림은 밀리초(ms) 단위의 초저지연이 필요한 온라인 게임이 아니라 **1~2초 이내의 반영이면 충분한 도메인**입니다. 따라서 무상태(Stateless) 기반의 **HTTPS REST API + 주기적 폴링(Polling)** 구조를 채택하여, 일시적인 네트워크 단절이 발생하더라도 다음 폴링 주기에 즉시 자동 복구되는 **내결함성(Fault Tolerance)**을 우선시했습니다."

### Q3. "인증에서 일반적인 ID/PW 로그인 대신 왜 API Key(`access_token`) 방식을 썼고, 왜 HTTPS가 필요한가요?"
> **모범 답변:**  
> "키오스크나 주방 디스플레이는 일반 사용자가 매번 ID/PW를 입력해 로그인하는 개인 PC가 아니라, **매장에 고정 설치된 무인·전용 단말기(M2M, Machine-to-Machine)**입니다. 따라서 사용자 계정 로그인보다 기기별 **사전 공유 API Key(`access_token` 헤더)**를 검증하는 방식이 실제 매장 환경에 더 적합합니다.  
> 단, API Key를 일반 HTTP로 전송하면 패킷 스니핑 시 키가 평문으로 탈취될 위험이 있으므로, 이를 방지하기 위해 **HTTPS(SSL/TLS) 암호화**를 함께 적용해 인증 헤더와 주문 데이터를 모두 암호화했습니다."
